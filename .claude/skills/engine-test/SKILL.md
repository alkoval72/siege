# Тесты к правилу движка

## 1. Найди правило

- Определи, какое правило проверяется, и найди его в `docs/spec.md` (§4-5) и в `.planning/ARCHITECTURE-TARGET.md` (§4).
- Если правило в документах описано неоднозначно или расходится с кодом, остановись и спроси владельца. Тест под догадку не пиши.

## 2. Составь список случаев

Для правила выпиши случаи до написания кода:
- допустимые ходы и позиции (правило разрешает);
- недопустимые (правило запрещает), минимум один на каждое условие запрета;
- край поля: клетки на радиусе поля и за ним;
- граничные значения: первый ход, пустое поле, высокие стопки, если правило их касается.

## 3. Напиши тесты

- Файл: `server/Siege.Engine.Tests/<Тип>Tests.cs`. Если файл есть, дополни его.
- Имя метода: `Метод_Условие_Результат`, например `Neighbors_AnyHex_ReturnsSixDistinctAdjacentHexes`.
- Однотипные случаи объединяй в `[Theory]` с `[InlineData]`.
- Один тест проверяет одно поведение. Структура: подготовка, действие, проверка, разделённые пустой строкой.
- Позиции строй через публичный API движка. В тестах не используй тематические названия фишек.

## 4. Прогони

1. Тесты класса: `dotnet test server/Siege.sln --filter "FullyQualifiedName~Siege.Engine.Tests.<Тип>Tests"`.
2. Если тест на новое поведение проходит до изменения кода движка, тест ничего не проверяет. Исправь тест.
3. После изменения кода: все тесты `dotnet test server/Siege.sln` и `dotnet format server/Siege.sln --verify-no-changes`.

Не ставь `Skip`, не удаляй и не ослабляй падающие тесты. Если тест падает из-за ошибки в движке, исправляй движок.

## 5. Отчитайся

Кратко перечисли: какие случаи покрыты, сколько тестов добавлено, результат прогона. Если какой-то случай не покрыт, назови его и объясни почему.
