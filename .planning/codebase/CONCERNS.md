# Технический долг и проблемы

**Analysis Date:** 2026-10-27

Состояние репозитория на момент анализа: реализован только каркас. В `server/Siege.Engine/` есть один тип `Hex` (`server/Siege.Engine/Hex.cs`), в `client/src/game/hex.ts` есть одна функция `hexToPixel`. Серверного проекта `Siege.Server`, БД, REST, SignalR, `GameState`, `Game.GetLegalMoves` и `Apply` пока нет. Поэтому большая часть рисков ниже относится к будущим этапам M1-M5 и выражена как «что нужно закрыть до старта», а не как ошибка работающего кода.

## Срочно: поддержка платформы

**.NET 8 выходит из поддержки:**
- Проблема: проект нацелен на `net8.0` (`server/Directory.Build.props`), `global.json` фиксирует SDK `8.0.100` с `rollForward: latestFeature`. По объявлению Microsoft, поддержка .NET 8 заканчивается 2026-11-10, то есть примерно через две недели после даты анализа.
- Файлы: `server/Directory.Build.props`, `global.json`, `server/Siege.Engine/Siege.Engine.csproj`, `server/Siege.Engine.Tests/Siege.Engine.Tests.csproj`
- Влияние: после окончания поддержки не выходят исправления безопасности для рантайма и SDK.
- Путь решения: решить владельцу, переходить ли сразу на .NET 10 (LTS, как предусмотрено в `CLAUDE.md` для планового перехода) или оставаться на 8 до конца поддержки. Затем обновить `TargetFramework`, `global.json` и пакеты тестов. Переход требует согласования, так как это смена версии платформы.

## Безопасность

**Защита секретов держится на одном hook'е с зависимостью от `jq`:**
- Риск: `.claude/hooks/protect-files.sh` блокирует `.env` через код выхода 2. Скрипт использует `jq` и `set -euo pipefail`. Если `jq` отсутствует, команда падает с кодом, отличным от 2. Такой код Claude Code, по документации, не блокирует вызов инструмента, то есть защита выключается молча. Поле `onFailure: "block"` в `settings.json` не входит в известную схему hook'ов, его действие не проверено.
- Файлы: `.claude/hooks/protect-files.sh`, `.claude/settings.json` (блок `PreToolUse`)
- Текущая защита: `permissions.deny` для `Read(.env*)`, `Edit(.env*)`, `Bash(cat .env*)` (префиксные правила) и regex в hook'е, который блокирует любое упоминание `.env` в Bash.
- Рекомендации: проверить поведение при отсутствии `jq` (тест с переменной PATH без `jq`), убрать неподтверждённое поле `onFailure`, рассмотреть проверку без зависимости от внешних утилит.

**Префиксные deny-правила обходятся:**
- Риск: правила вида `Bash(cat .env*)` срабатывают только на команду, начинающуюся с `cat`. Регулярка в `protect-files.sh` более широкая, но её тоже можно обойти, если имя файла собрано из кусков (кавычки, переменные). Hook защищает только `.env*` и `.git/`.
- Файлы: `.claude/settings.json`, `.claude/hooks/protect-files.sh`
- Что не защищено: файлы из списка `forbidden_files` в инструкциях агента (`*.pem`, `*.key`, `*.p12`, `credentials*`, `secrets*`, `.npmrc`, `.netrc`) защищены только инструкцией, но не hook'ом и не `permissions.deny`.
- Рекомендации: добавить в `permissions.deny` и в hook эти шаблоны. Это изменение конфигурации, его делает владелец.

**Широкие разрешения и режим `acceptEdits`:**
- Риск: `permissions.defaultMode` = `acceptEdits`, поэтому правки применяются без запроса. В `allow` есть `Bash(npm run *)`, `Bash(npx vitest *)`, `Bash(npx playwright test *)`, `Bash(npm --prefix client run *)`, `Bash(git add *)`, `mcp__playwright__*`. Шаблон `npm run *` разрешает запуск любого скрипта из `package.json`.
- Файлы: `.claude/settings.json`
- Текущая защита: `ask` для `git commit`, `git push`, `npm install`, `npm ci`, `dotnet add`, `docker`; `deny` для `rm -rf`, `git reset --hard`, `git clean`, `sudo`.
- Рекомендации: оставлять `acceptEdits` только при сохранении `ask` для установки пакетов; при появлении новых скриптов в `package.json` проверять, что `npm run *` не открывает неожиданных действий.

**MCP-сервер Playwright запускается без фиксации версии:**
- Риск: `.mcp.json` запускает `npx @playwright/mcp@latest`. Версия не закреплена, пакет подтягивается из сети при каждом запуске (supply chain).
- Файлы: `.mcp.json`, `.claude/settings.json` (`enabledMcpjsonServers`)
- Рекомендации: закрепить конкретную версию пакета и обновлять её осознанно.

**Токены игроков (этап M5, ещё не реализовано):**
- Риск: по `docs/architecture.md` §5.6 токен хранится в `localStorage`. Любой XSS в клиенте даст доступ к партии. Для SVG и Vue-шаблонов нужны правила работы с пользовательским вводом (имя игрока до 24 символов).
- Файлы (будущие): `client/src/api/http.ts`, `client/src/api/hub.ts`, `server/Siege.Server/`
- Рекомендации: в `docs/security-checklist.md` (запланирован в `docs/plan.md`) зафиксировать экранирование имени игрока, отсутствие `v-html` с пользовательскими данными, хранение только хеша токена (SHA-256, как в архитектуре), ограничения CORS и валидацию входа REST и SignalR.

**Нет проверки входных данных сервера (этап M4-M5, ещё не реализовано):**
- Риск: `docs/architecture.md` §5.2 описывает `SubmitMove(gameId, expectedVersion, move)`. Ход приходит как JSON с полем `kind`. Без явной валидации десериализации и границ координат (радиус из `GameOptions`) сервер может принять ход с координатами вне поля до проверки `GetLegalMoves`.
- Рекомендации: проверка через `GetLegalMoves` (как требует архитектура) должна стоять первым шагом, до любой работы с состоянием.

**Неизученные GSD hook'и:**
- Риск: `.claude/settings.json` подключает около 15 скриптов `.claude/hooks/gsd-*` (в том числе `gsd-prompt-guard.js`, `gsd-read-injection-scanner.js`, `gsd-validate-commit.sh`). Они не закоммичены (`git status` показывает их как `??`) и выполняются при каждом вызове инструмента. По задаче они исключены из анализа, аудита содержимого здесь не проводилось.
- Файлы: `.claude/hooks/gsd-*`, `.claude/settings.json`
- Рекомендации: отдельный аудит перед коммитом, в том числе чтения `gsd-validate-commit.sh`, который проверяет коммиты.

**Пустой `.gitignore` для `.env.example`:**
- Проблема: `.gitignore` разрешает `!.env.example`, а `protect-files.sh` блокирует любой `.env.*`, включая шаблон. Это не уязвимость, но разрешённый файл и заблокированный hook'ом путь не совпадают. Владелец решает, как вести шаблон.
- Файлы: `.gitignore`, `.claude/hooks/protect-files.sh`

## Проблемы производительности

Код производительности пока нет, поэтому пункты ниже относятся к решениям из архитектуры.

**Размер ответа `GameState` с `legalMoves`:**
- Проблема: `docs/architecture.md` §5.3 отправляет полный список `legalMoves` в каждом `GameState` игроку, чей ход. Поле 331 клетка, фишка `Runner` ходит на любое число шагов вдоль края, `Jumper` и `Scout` дают множество вариантов. Список может вырасти в сотни элементов на каждое обновление.
- Файлы (будущие): `server/Siege.Engine/` (`Game.GetLegalMoves`), `server/Siege.Server/` (`GameHub`)
- Путь решения: замерить размер списка на типичной позиции в тесте случайных партий (`docs/architecture.md` §9). Если нужно, вводить дельту или лимит.

**Вычисление `GetLegalMoves` при каждом запросе:**
- Проблема: по `docs/architecture.md` §4.4 точки сочленения (Тарьян) считаются один раз на позицию, но `legalMoves` вычисляется для каждого `GameState`. Кэширование по `version` не описано.
- Путь решения: кэшировать результат на `GameState` (он неизменяем, поэтому кэш безопасен) и считать ходы лениво.

**Восстановление партии из журнала ходов:**
- Проблема: `Game.Replay` (`docs/architecture.md` §4.3) воспроизводит все ходы при каждой загрузке сессии из БД, сложность растёт с длиной партии. Снимков нет (архитектурное решение «только ходы»).
- Путь решения: держать сессию в памяти (как сделано в `GameRegistry`), а восстановление из БД использовать только при перезапуске. Если партии станут длинными, пересмотреть решение «без снимков».

**Выгрузка сессий и рост памяти:**
- Проблема: `GameRegistry` держит активные партии в памяти и выгружает их через 30 минут без подключений (`docs/architecture.md` §5.5). Лимита на число сессий нет.
- Путь решения: добавить метрику числа сессий и ограничение, когда появится `Siege.Server`.

- Файлы: `docs/spec.md` §5.5, `docs/architecture.md` §4.1 и §6 (`games.board_radius`)

## Масштабирование

**Одна копия сервера:**
- Текущая ёмкость: одна копия сервера, все активные партии в памяти процесса (`docs/architecture.md` §2, §13).
- Ограничение: несколько серверов за балансировщиком не поддерживаются, сессии в памяти не разделяются.
- Путь масштабирования: для семейного проекта допустимо, по `docs/architecture.md` §13. При переходе на несколько копий понадобится общий слой состояния (например, Redis backplane для SignalR и синхронизация блокировки `SemaphoreSlim`, которая сейчас работает только внутри процесса).

**Одновременное выполнение ходов:**
- Ограничение: блокировка партии через `SemaphoreSlim` (`docs/architecture.md` §5.4) действует только в одном процессе. Версия (`expectedVersion`) защищает от устаревших ходов, но не от гонки при двух серверах.
